# Выдержки из журнала решений ProDisser (docs/DECISIONS.md, коммит f702268)

## Р-403 · Кнопка замечаний на сайте и в кабинете без персональных данных (04.10.2026)

*Принято в main под номером Р-277; перенумеровано при слиянии с веткой кабинета 05.10.2026 (Р-410): номера Р-277…Р-402 заняты решениями ветки. В истории коммитов main — прежний номер.*

**Решение: на время запуска на всех страницах сайта и всех экранах
кабинета справа внизу стоит кнопка «Оставить замечание». Замечание
записывается с временем, местом и предварительной критичностью; раз в
неделю замечания разбираются и исправляются точечно. Персональные данные
виджет не собирает.** Задача Э12 плана; принята 04.10.2026, к реализации
— по указанию заказчика того же дня.

### Почему

На запуске ошибки находят руководитель и первые клиенты и сообщают о них
кто как: в мессенджере, звонком, письмом. Место ошибки и её серьёзность
при этом теряются, повторы не видны. Одна кнопка с одной таблицей даёт
перечень, по которому правки идут по порядку важности.

### Решения заказчика

Кнопка видна всем и выключается одной настройкой сборки; персональные
данные не собираются; кроме времени, страницы и текста фиксируются
устройство и ширина окна и снимок экрана; критичность — правилами при
отправке, итоговая — на еженедельном разборе; таблица — экран в кабинете
и Excel на Диске.

### Как

- **Кнопка** (`components/FeedbackWidget.tsx`) — в общей разметке рядом
  со счётчиком Метрики, на всех страницах. Панель-диалог: «Замечание о
  странице», строка «Страница: …», поле «Что не так», для страниц сайта —
  «Снимок экрана (необязательно)», кнопка «Отправить». Ловушка Tab, Esc,
  возврат фокуса; одна кривая движения, `prefers-reduced-motion`.
- **Без персональных данных:**
  - замечание не связывается ни с учётной записью, ни с сессией; запрос
    уходит без cookies; IP служит только ключом ограничителя частоты в
    памяти и никуда не пишется; строка браузера не читается;
  - текст с телефоном, почтой или ссылкой на мессенджер не принимается:
    «Уберите из замечания телефон, почту или ссылку на мессенджер: виджет
    не собирает персональные данные.»;
  - страница пишется шаблоном пути (`lib/feedback.ts`, `pathTemplate`):
    ключ входа → `[ссылка]`, код работы → `[код]`, идентификаторы и
    сегменты, похожие на имя, почту или телефон, → `[id]`; запрос и якорь
    отбрасываются. Шаблон сводится и в браузере, и заново на сервере;
  - снимок экрана — только со страниц сайта: на экранах кабинета видны
    имена и суммы, и снимок оттуда был бы передачей персональных данных.
    Тип проверяется по сигнатуре (PNG, JPEG, WEBP), до 5 МБ, имя файла не
    хранится.
- **Что фиксируется:** момент, область (сайт или кабинет), шаблон
  страницы, текст (3–5000 знаков), устройство и ширина окна, снимок,
  критичность.
- **Критичность** (`autoSeverity`): правилами по словам и месту —
  «критично» (не работает, не отправляется, сбой, пропало, вход; деньги в
  кабинете), «высокая» (ошибка, не видно, налезает; страница входа),
  «низкая» (опечатка, пожелание), иначе «средняя». Правило сохраняется
  отдельно; на разборе ставится итоговая.
- **Разбор** — экран `/cabinet/manage/feedback` (действие
  `FEEDBACK_REVIEW`, только руководитель; пункт «Замечания» в
  «Управлении», раз в неделю): плитки «Новых», «В работе», «Критичных
  открытых», «Всего»; отбор; по строке — критичность, состояние («новое»,
  «в работе», «исправлено», «отклонено»), «Что сделано»; выгрузка .xlsx.
  В журнал пишутся переходы, без текстов.
- **Таблица на Диске** — «Замечания.xlsx» в зеркале (`feedbackTable`);
  в обезличенном режиме зеркала колонки со свободным текстом скрываются,
  как «Сообщение» и «Отзыв».
- **Приём** — `POST /api/feedback`: 10 замечаний на адрес за 10 минут,
  тело до 6 МБ (`deploy/nginx.conf` — отдельный предел для маршрута,
  применяется выкатом через `nginx-sync.sh`), ловушка и отметка времени,
  как у заявок. Наружу ничего не уходит.
- **Выключатель** — `NEXT_PUBLIC_FEEDBACK_WIDGET=off` при сборке
  (`deploy/.env` → `docker-compose.yml` → `Dockerfile`): кнопки нет,
  приём отвечает 404.

### Проверено

`feedback.test.ts` — шаблон пути, область, устройство, критичность,
сигнатуры снимка, приём на настоящем запросе; `feedback.db.test.ts` —
запись, отказ снимка из кабинета, разбор, права, таблица зеркала без IP и
строки браузера. В браузере: виджет на 360, 390 и 1440 px без
горизонтальной прокрутки, axe без нарушений, Tab, Esc и возврат фокуса.


## Р-405 · Замечания для исполнителя правок: выгрузка и разбор по ключу (04.10.2026)

*Принято в main под номером Р-279; перенумеровано при слиянии с веткой кабинета 05.10.2026 (Р-410): номера Р-277…Р-402 заняты решениями ветки. В истории коммитов main — прежний номер.*

**Решение: исполнитель правок (Claude Code в облачной среде) получает
замечания с кнопки и отмечает их разбор сам, по отдельному ключу
`FEEDBACK_EXPORT_TOKEN`, без учётной записи в кабинете. Ключ открывает
только замечания.** Указание заказчика от 04.10.2026: «чтобы по запросу
ты мог их все видеть и работать с ними»; разрешение на чтение и правку
разбора дано тем же днём.

### Почему

Замечания нужны тому, кто по ним правит код. Пересылать раз в неделю
выгрузку .xlsx в переписку — лишний шаг для руководителя и задержка до
недели. Учётная запись руководителя для исполнителя открыла бы весь
кабинет: заявки, клиентов, деньги. Отдельный ключ даёт ровно одно —
замечания, в которых персональных данных нет по Р-403.

Другие пути отвергнуты:

- **Артефакт GitHub Actions по ssh** — репозиторий открытый (Р-264):
  выгрузку мог бы скачать любой вошедший в GitHub; ключ выката к тому же
  привязан к одной команде обновления (DEPLOY.md, 5г) и расширять его
  нельзя.
- **Файл «Замечания.xlsx» на Диске** — ключ Диска открывает всю папку
  практики, включая книгу заказов; выдавать его исполнителю нельзя.

### Как

- **Адреса** (`app/api/feedback/export/…`, правила — `lib/feedback-export.ts`):
  - `GET /api/feedback/export[?status=…]` — перечень, свежие сверху, до
    5000 строк; время по Москве, подписи — как в таблице на Диске; ключ
    хранилища снимка наружу не отдаётся;
  - `GET /api/feedback/export/<id>/screenshot` — снимок, `nosniff`;
  - `PATCH /api/feedback/export/<id>` — `{status?, severity?, note?}`,
    недостающие поля остаются прежними; проверки и момент закрытия — те же,
    что у разбора руководителем (`applyReview`).
- **Ключ** — `Authorization: Bearer <ключ>`; сравнение отпечатков SHA-256
  за постоянное время. Ключ не задан или короче 32 знаков — адреса нет;
  неверный ключ — тот же 404. Предел — 300 запросов на адрес за 10 минут,
  до проверки ключа. Ответы — `private, no-store`, `noindex`.
- **Журнал**: выгрузка перечня — `FEEDBACK_EXPORTED` с числом строк, разбор
  — `FEEDBACK_REVIEWED`; действующего лица нет («система»), в данных
  пометка `via: key`.
- **Настройка**: `deploy/.env` → `docker-compose.yml` → контейнер; тот же
  ключ — переменной в облачной среде, `prodisser.ru` — в её сетевом доступе
  (DEPLOY.md, 5ж). Отчёт цепочки при выкате пишет, включена ли выгрузка и
  видит ли ключ работающее приложение (значение не печатается).
- **Утилита** `tools/feedback-pull.mjs`: выгрузка со снимками в
  `feedback-export/` (в `.gitignore`) и перечень в терминал; режим
  `review <id> status=… severity=… note=…`.

### Проверено

`feedback-export.test.ts` — ключ (совпал, не задан, короткий, чужой, иная
схема), разбор отбора и правки, ответы на настоящих запросах: 404 без ключа
и с чужим без обращения к базе, 429 до проверки ключа, заголовки, 400, 404
и 413 у разбора. `feedback.db.test.ts` — перечень и отбор, частичный разбор
с моментом закрытия, журнал «по ключу», снимок. На стенде (сборка, база
`prodisser_e2e`): утилита забрала четыре замечания и снимок, байт в байт
совпавший с отправленным; разбор записан и отражён в журнале; без ключа и с
чужим ключом — 404.


## Р-583 · Отработанные замечания отмечены исправленными (14.10.2026)

**Указание владельца 14.10.2026**: «в замечаниях отмечать те пункты,
которые отработаны уже». В выгрузке замечаний от 14.10.2026 из 32 строк
«исправлено» стояло у одной: правки по остальным выпущены решениями
Р-478…Р-495 (09.10), Р-552…Р-565 (12.10) и Р-572…Р-582 (14.10), а
состояние в базе никто не поставил. Разбор пишется на экране «Замечания»
или ключом выгрузки (Р-405); ключа у исполнителя кода нет.

**Решение.** Миграция данных `20261014130000_feedback_review_release`
ставит тридцати отработанным замечаниям:
- состояние «исправлено»;
- «что сделано» — номер решения и одна-две фразы о правке;
- дату закрытия — время слияния выпуска с правкой (PR #212 —
  08.10 21:59 UTC, PR #213 — 08.10 23:16 UTC, PR #217 — 12.10 19:02 UTC);
  правки выпуска 14.10 (PR #224) закрываются временем выката;
- запись «Замечание разобрано» в журнал действий без действующего лица,
  с пометкой `via = release` — как разбор ключом (`via = key`, Р-405).

Критичность не меняется.

Почему миграция, а не разбор на экране или ключом:
- она идёт тем же выкатом, что и проверка здоровья схемы (Р-218), и не
  требует передавать ключ выгрузки в переписку;
- состав и тексты проверяются в CI до выката, а не набираются руками
  тридцать раз.

Ограничения, которые держат миграцию безопасной:
- трогаются только замечания в состоянии «новое»: если руководитель уже
  разобрал замечание на экране, его разбор не перетирается;
- повторный прогон ничего не меняет;
- на базе без этих замечаний (CI, снимки, разработка) миграция ничего не
  делает;
- одна инструкция — проверка прогоняет файл на базе целиком.

**Не отмечено**: фотографии реальных клиентов в отзывах (замечание
04.10.2026). Нужны снимки и письменное согласие изображённых
(ст. 152.1 ГК РФ); копировать фото с площадок нельзя (Р-113). Замечание
остаётся «новым» до материалов владельца.

### Что сделано

- `app/prisma/migrations/20261014130000_feedback_review_release/migration.sql`.
- `schema-version.ts` — `LATEST_MIGRATION` поднят.
- `tests/feedback-release-review.test.ts`: тридцать идентификаторов без
  повторов; замечание о фотографиях не тронуто; каждое «что сделано»
  начинается с решения, решение есть в своде, длина не больше `NOTE_MAX`;
  только «новые»; одна инструкция.
- `tests/feedback-release-review.db.test.ts`: на настоящей базе «новое»
  закрывается с текстом и датой (время выката — в UTC, без сдвига на
  пояс), разобранное руководителем остаётся, журнал пишет две записи с
  `via = release` и прежней критичностью, повторный прогон записей не
  добавляет. Замечания с такими идентификаторами в проверяемой базе
  проверка не трогает.
